# Subchat — Spec

Component for running headless subagents within a session. Generic — used by all sub-agent use cases (protocolist now; advisor, coder, reviewer in the future).

## Purpose

When the main session needs to delegate work to another agent, subchat provides:

- a CLI wrapper that invokes `claude -p` for a named subagent;
- a per-subagent folder under the SessionFolder for config, session state, run history;
- isolation of the subagent from the main agent's `.claude/` configuration;
- live stdout streaming so the parent (the main agent watching via Monitor) sees the subagent is alive and progressing.

Without this component, every parallel-chat use case would re-invent claude command construction, `session_id` management, config file layout, output capture, and progress streaming. Subchat centralizes all of that.

## CLI

```
subchat --subagent <name> --msg "<text>" [--session-folder <path>]
```

- `--subagent` — name of the subagent profile, identifies the folder under `<SessionFolder>/subchats/`. Required.
- `--msg` — the message to deliver to the subagent. Required. Typically a verbatim translation of what the user wrote (e.g., `!протокол`, `!протокол финиш`).
- `--session-folder` — optional absolute path to the SessionFolder. If omitted, subchat uses its own cwd. Both forms are equivalent; the explicit form is for callers that aren't already in the SessionFolder.

Exit code: 0 on successful claude run; non-zero propagates the claude exit code or signals a subchat-internal error.

## Folder layout

Inside the SessionFolder, per active subagent:

```
<SessionFolder>/
  subchats/
    <subagent>/                ← e.g., protocolist
      config.yaml              ← all settings, fully explicit
      system_prompt.md         ← subagent's system prompt, copied from instructions/subagents/<subagent>.md body
      session.json             ← claude session_id (appears after first run)
      log/                     ← run history (subchat-owned; MCP does not touch)
        01/
          prompt.md
          output.json
          response.md
          meta.json
        02/
          ...
```

The folder is created by MCP `spawn_subchat` (see `mcp.md`). `log/` is created lazily by subchat on its first run.

## `config.yaml` schema

Generated by MCP from the subagent profile's frontmatter (defaults filled in). All fields explicit — full visibility for control and debugging.

```yaml
model: sonnet                       # claude model
system-prompt: system_prompt.md     # path to full-replace system prompt (relative to subchat dir)
append-system-prompt: null          # alternative: append to harness default
max-turns: null                     # max model turns per invocation; null = unlimited
allowed-tools: [Read, Write, Edit, Bash, Glob, Grep]
disallowed-tools: []
permission-mode: null               # claude permission mode
bare: false                         # --bare flag
effort: max                         # effort level (env var)
cwd: ../..                          # relative to subchat folder; ../.. = SessionFolder
no-session-persistence: false
env: {}                             # extra env vars
output-format: stream-json          # claude output format; stream-json is required for live [tool]/[assistant] events
```

Any field absent in the profile frontmatter falls to the default shown above. Subchat reads `config.yaml` on every invocation — changes take effect on the next run without restart.

**Path resolution.** All path-valued fields (`system-prompt`, `append-system-prompt`, `cwd`) are written in `config.yaml` as relative paths anchored at **the subchat folder itself** (`<SessionFolder>/subchats/<subagent>/`). This makes the config self-locating and human-readable. Subchat resolves them to absolute paths before passing to `claude` — claude's own cwd is set by the `cwd` field, so a relative `system-prompt` would otherwise resolve against claude's cwd, not the config's location. The resolution rule: `os.path.abspath(os.path.join(<subchat-folder>, value))` (use `abspath`, not `realpath` — symlink resolution would surprise if a subchat folder is ever symlinked to a shared template).

## `session.json` schema

```json
{
  "session_id": "<UUID>",
  "created": "<ISO timestamp>"
}
```

Absent before the first claude run. Created and populated by subchat on the first successful run (parsing `session_id` from claude's output). Persists across subsequent runs; `--resume <session_id>` is appended to the claude command when this file exists.

## `log/NN/` per-run files

`NN` is zero-padded sequential run number. Each run gets its own folder.

| File | Content |
|---|---|
| `prompt.md` | The `--msg` text, persisted before claude is spawned (replay-safe). |
| `output.json` | Claude's full JSON output for this run (when `output-format: json`). |
| `response.md` | The `result` field extracted from `output.json` — human-readable text reply. |
| `meta.json` | Run metrics: `duration_ms`, `exit_code`, `flags`, `tokens` (input/output/cache), `cost_usd` (when available). |

## Stdout streaming contract

While running, subchat emits progress events to its own stdout, one per line, prefix-tagged. These are subchat's messages to its parent (the main agent watching via Monitor) — not claude's raw output. Claude's raw output is captured into `log/NN/output.json`.

Required event categories:

| Tag | When | Required |
|---|---|---|
| `[start]` | At invocation: `[start] subagent=<name> run=NN msg=<truncated>` | always |
| `[claude-spawn]` | When `claude -p` is about to launch: `[claude-spawn] flags=<short>` | always |
| `[tool]` | Each tool call observed in claude's stream: `[tool] <name>` | when `output-format: stream-json` |
| `[assistant]` | Each assistant text chunk in claude's stream: `[assistant] <first 80 chars>...` | when `output-format: stream-json` |
| `[heartbeat]` | At a fixed interval (default every 10s) while waiting for claude output, when nothing else has been emitted: `[heartbeat] elapsed=<seconds>` | when `output-format: json` (non-streaming) |
| `[warn]` | Non-fatal issues (e.g., field defaults applied): `[warn] <message>` | always |
| `[error]` | Fatal issues: `[error] <message>` | always |
| `[complete]` | At run completion: `[complete] run=NN exit=<code> duration_ms=<N>` | always |

The parent process (typically the main agent's Monitor) sees these as a live progress log. The discipline: **never go silent** for more than a few seconds — emit `[tool]` / `[assistant]` events as claude proceeds (or `[heartbeat]` if streaming is disabled) so the human watching the chat knows work is happening.

**Output-format coupling.** Live `[tool]` / `[assistant]` attribution is only possible when claude runs with `--output-format stream-json` — subchat parses each line of that stream as it arrives. With `--output-format json` (single blob at end), there are no intermediate events to surface; subchat falls back to `[heartbeat]` while the model is silent. Subagents whose user-facing contract guarantees live progress (e.g., `protocolist`) **must** declare `output-format: stream-json` in their profile frontmatter.

## Isolation discipline

`claude -p` is launched with cwd set to the SessionFolder (`cwd: ../..` in `config.yaml`, resolved relative to the subchat folder). This means:

- Claude does not see `<Igor.cockpit>/.claude/` (which would inject Igor's output-style and hooks);
- Claude sees the SessionFolder contents (`transcript/`, `state.md`, `protocol.md`, OBJ files if accessed via relative paths, etc.);
- Claude sees its own subchat folder (`subchats/<name>/`).

System prompt comes from `system_prompt.md` (full-replace via `--system-prompt-file`). The subagent's behavior is fully defined there — harness defaults are not present. The subagent's body must include any necessary discipline (non-interactive Bash, tool-use reminders) since the harness safety prompt is replaced.

## Lifecycle

1. **Spawn (one-time).** MCP `spawn_subchat(subagent="<name>")` creates `<SessionFolder>/subchats/<name>/` with `config.yaml` and `system_prompt.md`. Adds the subagent to `state.md` `## Subchats`. `session.json` and `log/` are absent at this point.

2. **First run.** Subchat is invoked with `--subagent <name> --msg "<text>"`. Allocates `log/01/`, writes `prompt.md`, runs `claude -p` (no `--resume`), captures output, extracts `session_id`, writes `session.json`.

3. **Subsequent runs.** Allocates next `log/NN/`. Reads `session.json`, appends `--resume <session_id>` to the claude command. Same subchat session continues — Claude sees full prior conversation as context.

4. **Active for the lifetime of the SessionFolder.** No explicit teardown — the subchat folder persists in the journal alongside the session.

## `state.md` integration

Subchat presence is tracked in `state.md` under a new section `## Subchats` (see `schemas/session_folder.md`). Format:

```
## Subchats
- protocolist (active)
```

Minimal: subagent name + state (`active` / `terminated`). MCP `spawn_subchat` writes the entry; subchat operations do not modify this section.

## Concurrency

Two `subchat` processes for the **same** `<SessionFolder>/subchats/<name>/` must never run simultaneously — they would race on `log/NN` allocation, `session.json` writes, and (for protocolist) on `transcript/index.json` and `protocol.md`. This is guarded by a lightweight lock:

- On startup, after resolving the subchat folder, subchat attempts to create `<SessionFolder>/subchats/<name>/run.lock` as an empty file via `O_CREAT | O_EXCL` (atomic on POSIX). The file content is a single line: `pid=<PID> started_at=<ISO>`.
- If the create succeeds — subchat owns the lock for this run. On normal exit *and* on any abnormal exit (signal, crash, error), subchat removes `run.lock` in a `try/finally`.
- If the create fails with `EEXIST` — another subchat run is in flight. The new invocation refuses: emits `[error] concurrent subchat run detected — see run.lock`, exits non-zero, does **not** allocate `log/NN`, does **not** call claude. There is no queue; the caller decides whether to retry.
- **Stale lock recovery.** If `run.lock` exists and references a `pid=` value that is not currently a running process (per `kill -0 <pid>`), the new invocation logs `[warn] stale run.lock removed (pid=<N> not alive)`, deletes the file, and re-tries the atomic create exactly once. Cross-host scenarios are out of scope.

Concurrent runs across **different** subagents within the same SessionFolder are allowed — each subagent has its own `run.lock` under its own subchat folder.

`log/NN/` allocation under a held lock: subchat reads `log/` entries, takes `max(NN) + 1`, and creates the new folder via `os.makedirs(...)`. Under the lock there is no race; without the lock the operation would be unsafe and is explicitly forbidden.

## Error handling

| Condition | Behavior |
|---|---|
| Subchat folder missing (`subchats/<name>/` does not exist) | Refuse; exit non-zero; surface `[error] subchat folder missing — run spawn_subchat first`. |
| `config.yaml` missing required fields | Apply defaults from schema; emit `[warn]` for each. |
| Claude exit != 0 | Capture `exit_code` in `meta.json`; emit `[error] exit=<code>`; subchat returns same code. |
| Claude output JSON malformed | Save raw to `log/NN/output.raw`; emit `[error] malformed output`. |
| Filesystem write error (atomic-rename fail) | Emit `[error]`, abort current run. State files (`session.json`) are never partially written. |

## Out of scope (v1)

- Multiple concurrent subagents of the same name within one session: not supported. One subchat per `<subagent>` per `<SessionFolder>`.
- Subagent → subagent recursion.
- Cross-SessionFolder subchat reuse.
- Subchat persistence beyond the SessionFolder (journal archives the SessionFolder; subchat history archives with it).
